# Project change log

Update `changelog.md` whenever a user-facing gameplay, interface, content, balance, or bug fix is completed. Keep `full_changelog.txt` as the older reference rather than updating both versions.

The changelog presents the complete released changes from TRIGGERED P's final CruS Online commit (`94779919bb75278ea69328f4ce53611b9d6d963b`, upstream/main) to the current Revitalized build. It is a consistent public overview of the expansion, not a chronological account of requests or development iterations.

- Check the original baseline before calling something new. Describe inherited systems as expanded, reworked, or fixed when appropriate
- Group a feature's resulting behavior into one or a few cohesive bullets. Fold fixes to newly introduced, unreleased features into their descriptions instead of listing the development problems separately
- Cover additions, changes, balance changes, removals, and fixes to original behavior. Keep meaningful gameplay details without narrating intermediate layouts, abandoned attempts, or implementation housekeeping
- Describe achievement additions by their full scope and related groups. Do not single out an achievement merely because its implementation was recently corrected
- Individual equipment abilities and voice effects can have separate bullets because they describe distinct behavior players need to compare
- Use uppercase topic headings, Markdown bullets, direct public-facing language, and readable in-game names. Do not end a bullet with a period
- Keep the same level of detail across related features. Avoid repeating the same change in several categories or adding vague filler to imply completeness
- Verify claims against the current code and content. Do not describe planned or placeholder features as finished, or list inherited features as Revitalized additions
